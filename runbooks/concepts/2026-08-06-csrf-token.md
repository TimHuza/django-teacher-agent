Definition:
A CSRF token is a unique, secret, and unpredictable string of characters generated by the server. It is placed inside HTML forms and validated when those forms are submitted.

Why It Exists:
It protects websites from Cross-Site Request Forgery (CSRF) attacks. Without this protection, a malicious website could trick a user's web browser into making unauthorized requests (like changing a password or buying a product) to another website where the user is currently logged in.

Simple Explanation:
Imagine you have signed a blank check at your bank, and anyone who finds it can write their name and any amount of money to steal from you.
A CSRF token is like a secret security phrase or physical stamp that the bank teller gives you when you walk into the bank. Every time you want to withdraw money or make a transfer, you must show this unique stamp. Since an attacker on another website doesn't have your unique physical stamp, the bank teller will instantly reject any request they try to send on your behalf.

Django Example:
In Django, you protect a form by adding the `{% csrf_token %}` template tag inside your `<form>` element:

```html
<form method="post" action="/submit-feedback/">
    {% csrf_token %}
    <label for="feedback">Your Feedback:</label>
    <input type="text" id="feedback" name="feedback">
    <button type="submit">Submit</button>
</form>
```

When Django renders this template, the `{% csrf_token %}` tag is replaced with a hidden input field that contains the actual token value:

```html
<input type="hidden" name="csrfmiddlewaretoken" value="aBC123xyz789...">
```

How Django Uses It:
1. When a user logs in or visits a page with a form, Django generates a secret CSRF cookie and stores it in their browser.
2. In the template, `{% csrf_token %}` inserts the same value into a hidden form field.
3. When the form is submitted via `POST`, Django's built-in `CsrfViewMiddleware` intercepts the request.
4. Django compares the token in the form data (`csrfmiddlewaretoken`) with the token in the user's cookie.
5. If the tokens match, Django knows the request came genuinely from your own website's form. If they do not match, or if the form token is missing, Django rejects the request with a `403 Forbidden` error.

Common Mistakes:
- **Forgetting the tag**: Forgetting to add `{% csrf_token %}` inside a `POST` form. This results in a `403 Forbidden` error.
- **Using it on GET forms**: Putting the token inside standard search or filter forms that use the `GET` method. GET forms should be "read-only" and do not require CSRF protection.
- **AJAX requests without headers**: Forgetting to read the CSRF cookie and include it as an `X-CSRFToken` HTTP header when making modern JavaScript API calls (like `fetch` or Axios).
- **Disabling the middleware globally**: Disabling `CsrfViewMiddleware` in `settings.py` block list to quickly get around errors, exposing the entire application to security risks.

Best Practices:
- Always keep the `CsrfViewMiddleware` enabled in your `MIDDLEWARE` settings.
- Use the `@csrf_protect` decorator if you need custom view-level protection.
- Use `@csrf_exempt` only when absolutely necessary (for example, for third-party webhook endpoints) and use alternatives like signature validation or API keys instead.
- Ensure all state-changing actions (creating, updating, deleting) use `POST`, `PUT`, or `DELETE` methods, and never `GET`.
- For REST APIs, fetch the CSRF token from the cookie or custom headers when issuing insecure requests.

Key Takeaways:
- CSRF is a vulnerability where malicious sites trick browsers into performing actions.
- A `csrf_token` serves as a secure, temporary stamp that verifies form submissions originate only from your site.
- In Django, adding `{% csrf_token %}` is mandatory for all `POST` forms.
